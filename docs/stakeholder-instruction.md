# Інструкція для стейкхолдера: Promo Design Brief Generator

## 1. Що вирішує проект

Promo Design Brief Generator — це внутрішній інструмент Universe Group для швидкого створення дизайн-брифів під promo-креативи вакансій і автоматичного заведення задач у Notion для Brand Design команди.

Інструмент закриває ручний процес:

1. Рекрутер або маркетинг дає текст вакансії чи Ashby-лінки.
2. Застосунок витягує опис вакансій, якщо це Ashby-лінки.
3. AI генерує структурований бриф для дизайнера.
4. Користувач перевіряє і редагує бриф.
5. Застосунок створює задачу або пакет задач у Notion з уже заповненими дефолтними полями.

На виході дизайнер отримує не просто текст, а готову Notion-задачу з брифом, пріоритетом, дедлайном, платформою, форматом, типом задачі і, якщо вакансій кілька, розподілом на child-задачі.

## 2. Які застосунки та сервіси задіяні

| Сервіс | Роль у процесі |
| --- | --- |
| Web app / Next.js | Основний інтерфейс для користувача. Тут вставляються вакансії, генерується бриф і запускається створення задачі. |
| Ashby | Джерело вакансій. Якщо користувач вставляє публічні Ashby-лінки, застосунок сам підтягне назву, опис, локацію, команду та інші доступні дані. |
| OpenRouter | AI-шар для генерації брифів. За замовчуванням використовується модель `anthropic/claude-sonnet-4.6`, якщо не задано іншу модель у змінних середовища. |
| Notion | Фінальне місце роботи дизайнера. Застосунок створює задачі в базі Brand Design Hub. |
| Browser localStorage | Зберігає системний промпт і історію останніх запитів локально в браузері користувача. |

## 3. Основний сценарій роботи

1. Користувач відкриває застосунок.
2. На першому екрані вставляє текст вакансії або один чи кілька публічних Ashby-лінків.
3. За потреби відкриває блок "Системний промпт" і коригує правила генерації.
4. Натискає "Згенерувати бриф".
5. Застосунок:
   - знаходить Ashby-лінки в інпуті;
   - завантажує дані вакансій з Ashby;
   - генерує окремий бриф для кожної вакансії;
   - зберігає результат в історію запитів.
6. На другому екрані користувач переглядає і редагує бриф.
7. На третьому екрані користувач заповнює параметри задачі для Notion.
8. Після натискання "Створити задачу в Notion" застосунок створює задачу або пакет задач і показує посилання для відкриття в Notion.

## 4. Екрани застосунку

### Екран 1: "Вакансії"

На цьому екрані користувач готує інпут для генерації.

Що є на екрані:

- Stepper з трьома кроками: "Вакансії", "Бриф", "Notion".
- Блок "Системний промпт" у вигляді розкривного блоку.
- Поле "Вакансії від рекрутера".
- Кнопка "Згенерувати бриф".
- Статус генерації: loading, success або error.

Що можна вставляти:

- plain text з описом вакансії;
- кілька вакансій одним текстом;
- публічні Ashby-лінки;
- мікс тексту і лінків.

Якщо користувач вставляє Ashby-лінки, застосунок сам витягує з них основний опис вакансій і передає його в генерацію.

### Екран 2: "Бриф"

На цьому екрані користувач перевіряє результат перед створенням задачі.

Якщо вакансія одна:

- показується один великий editable textarea з повним брифом;
- користувач може вручну відредагувати текст перед відправкою в Notion.

Якщо вакансій кілька:

- показуються окремі блоки по кожній вакансії;
- кожен блок має назву вакансії;
- якщо вакансія була з Ashby, під назвою показується source URL;
- кожен блок редагується окремо;
- застосунок одразу показує, скільки child-задач буде створено в Notion.

Логіка брифу:

- для кожної вакансії генерується рівно 3 креативні концепції;
- назви вакансій зберігаються дослівно;
- бриф пишеться українською і в Markdown-структурі;
- у брифі є суть ролі, інсайти, hook, visual direction, тексти на креативі, CTA, формат і нотатки дизайнеру.

### Екран 3: "Notion"

На цьому екрані користувач задає параметри майбутньої Notion-задачі.

Поля на екрані:

| Поле | Як працює |
| --- | --- |
| Назва задачі | Автоматично підставляється після генерації. Для однієї вакансії це назва вакансії, для кількох — пакетна назва у форматі "Промо вакансій [місяць] [рік]". Можна змінити вручну. |
| Deadline | Обов'язкове поле, користувач обирає дату. |
| Priority | Select. Дефолтне значення — `Planned`. |
| Platform | Select. Дефолтне значення — `Meta`. |
| Format | Сегментований вибір. Дефолтне значення — `Static Image`. |
| Task Type | Обов'язковий вибір типу задачі. Від нього залежить relation у Notion і оцінка в годинах. |

Доступні Priority:

- `Planned`
- `This week`
- `Urgent`
- `High`
- `Normal`
- `Low`

Доступні Platform:

- `Meta`
- `LinkedIn`
- `Telegram`
- `TikTok`

Доступні Format:

- `Static Image`
- `Square`
- `Stories`
- `Carousel`
- `Reels`
- `Video`
- `Animation`

Доступні Task Type:

| Task Type | Орієнтовна оцінка |
| --- | --- |
| Promo Creatives. Static нові ідеї | 2 год |
| Promo Creo Static (по шаблону) | 1 год |
| Promo Creo Video | 3 год |
| Promo Creatives. Video по шаблону | 1 год |
| Promo Creatives. Mix по шаблону | 1 год |
| Promo Creo Mix (нові ідеї) | 2.5 год |

Після успішного створення задачі екран змінюється на success state:

- показується повідомлення "Задачу створено" або "Задачі створено";
- є кнопка "Відкрити в Notion";
- якщо створені child-задачі, показується список окремих посилань на кожну child-задачу;
- є кнопка "Створити нову задачу".

## 5. Що створюється в Notion

### Якщо в інпуті одна вакансія

Застосунок створює одну Notion-задачу.

У задачі одразу заповнюються:

| Notion поле | Значення |
| --- | --- |
| Name | Назва з форми. За замовчуванням — назва вакансії. |
| Team | `Brand Design` |
| Status | `To do` |
| Priority | Значення, обране користувачем. Дефолт — `Planned`. |
| Owner | Дефолтний відповідальний користувач, налаштований у застосунку. |
| Deadline | Дата, обрана користувачем. |
| Platform | Значення, обране користувачем. Дефолт — `Meta`. |
| Format | Значення, обране користувачем. Дефолт — `Static Image`. |
| Task Type | Relation на обраний тип задачі. |
| Design needed | `true` |
| Design Briefed | `true` |
| Description | Коротка примітка: "Повний бриф додано нижче в тілі задачі." |

Повний бриф додається не тільки в property, а в тіло Notion-сторінки окремим блоком після divider з заголовком "Full design brief". Це зроблено, щоб не впиратися в обмеження довжини Notion rich text і щоб дизайнеру було зручно читати бриф у page body.

### Якщо в інпуті кілька вакансій

Застосунок створює:

1. Parent-задачу для всього пакету.
2. Окрему child-задачу для кожної вакансії.

Parent-задача містить:

- назву пакету;
- кількість вакансій;
- список вакансій;
- source URL для вакансій з Ashby;
- пояснення, що повні брифи лежать у child pages.

Child-задачі:

- мають назву конкретної вакансії;
- прив'язані до parent-задачі через Notion relation `Parent item`;
- мають ті самі базові поля, що й parent;
- містять повний окремий бриф тільки для своєї вакансії;
- доступні окремими посиланнями на success screen.

Це важливо для дизайнера: одна роль = одна child-задача = один окремий бриф і окремий production flow.

## 6. Як розподіляється робота по сабтасках

Розподіл відбувається автоматично на основі кількості згенерованих vacancy briefs.

Якщо після генерації є 1 vacancy brief:

- створюється тільки single task;
- parent/child структура не використовується.

Якщо після генерації є 2+ vacancy briefs:

- створюється parent task;
- для кожної вакансії створюється child task;
- child task отримує relation на parent task;
- у child task потрапляє тільки бриф відповідної вакансії;
- користувач бачить окремі посилання на всі child task у фінальному success state.

Приклад:

В інпуті 3 Ashby-лінки:

- Parent: `Промо вакансій Травень 2026`
- Child 1: точна назва вакансії 1
- Child 2: точна назва вакансії 2
- Child 3: точна назва вакансії 3

Усі задачі мають однакові обрані користувачем параметри: deadline, priority, platform, format і task type.

## 7. Історія запитів

Під основним flow є блок "Історія запитів".

Він показує:

- останні запити користувача;
- дату і час створення;
- інпут вакансій;
- згенерований аутпут;
- системний промпт;
- час генерації;
- час створення Notion-задачі;
- посилання на Notion-задачу;
- список child-задач, якщо вони були створені.

Історія зберігається локально в браузері користувача і не є спільною базою для всієї команди. Максимально зберігається 30 останніх записів.

## 8. Що важливо знати стейкхолдеру

- Інструмент не замінює фінальну вичитку: перед створенням задачі користувач може і має переглянути бриф.
- Назви вакансій не змінюються і не перекладаються, щоб не ламати рекрутинговий контекст.
- Якщо використовується Ashby, лінки мають бути публічними.
- Якщо AI-відповідь дуже довга, застосунок уміє дозапитувати продовження, але є технічний ліміт: максимум 3 continuation attempts.
- Якщо вакансій дуже багато, зараз підтримується до 30 Ashby-лінків за один запит.
- Якщо Notion API не може додати повний бриф у тіло задачі, застосунок покаже warning, але сама задача може бути створена.

## 9. Мінімальні умови для роботи

Для стабільної роботи потрібні:

- `OPENROUTER_API_KEY` — ключ для генерації брифів;
- `NOTION_TOKEN` — інтеграційний токен для створення задач у Notion;
- доступ Notion integration до Brand Design Hub database;
- актуальний Notion template для задач;
- коректні значення relation для Task Type;
- публічні Ashby-лінки, якщо інпут іде через Ashby.

Опційно:

- `OPENROUTER_MODEL` — модель генерації;
- `OPENROUTER_TIMEOUT_MS` — timeout для довгих запитів;
- `OPENROUTER_SITE_URL` — URL деплою для OpenRouter analytics;
- `NEXT_PUBLIC_APP_TITLE` — назва застосунку в інтерфейсі.

## 10. Очікуваний результат

Після проходження flow стейкхолдер має отримати:

- згенерований і відредагований дизайн-бриф;
- одну Notion-задачу, якщо вакансія одна;
- parent task і child task по кожній вакансії, якщо вакансій кілька;
- заповнені дефолтні поля для Brand Design процесу;
- повний бриф у тілі кожної релевантної Notion-задачі;
- посилання на створені задачі;
- локальний запис в історії запитів.

Фактично це перетворює сирий рекрутинговий інпут у готову до виконання design task structure для Brand Design команди.
